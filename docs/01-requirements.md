# Спецификация требований ContentFlow AI

Версия документа: **1.0** (ЛР2). Номера FR, NFR и US не меняются до конца семестра.

Состояние требований приведено на момент начала ЛР2 (код из ветки `main` после ЛР1). Значения:
- **есть** — работает и проверяется по признаку выполнения;
- **доработать** — функция есть, но признак выполнения не соблюдается полностью;
- **сделать** — функции нет.

## 1. О приложении

### Задача

ContentFlow AI помогает владельцам малого бизнеса регулярно вести соцсети без копирайтера. Пользователь один раз описывает бизнес, а сервис с помощью LLM пишет посты, составляет контент-планы и разбирает, какие публикации Telegram-канала набирают больше всего просмотров.

### Роли

| Роль | Описание |
|---|---|
| Пользователь | Владелец бизнеса или SMM-специалист. Регистрируется по email, ведёт до двух бизнесов, генерирует для них контент |
| LLM-провайдер (внешняя система) | OpenRouter: по промпту возвращает текст поста или список идей |
| Telegram (внешняя система) | Отдаёт посты публичного канала с числом просмотров |
| Почтовый сервер (внешняя система) | Доставляет письма с кодами подтверждения и сброса пароля |

### Что приложение умеет на начало ЛР2

Регистрация с подтверждением email, вход, сброс пароля; создание, редактирование и удаление до двух бизнесов, выбор активного; генерация поста для бизнеса; генерация контент-плана (идеи без дат); анализ Telegram-канала и генерация постов по выбранным популярным публикациям. История постов хранится только в браузере, история контент-планов отсутствует. Без внешних ключей приложение работает в демо-режиме (см. README).

### Термины

| Термин | Сущность в коде | Значение |
|---|---|---|
| Пользователь | `User` (auth_service) | Учётная запись: имя, email, хэш пароля, признак подтверждения email |
| Бизнес | `BusinessModel` (business_service) | Профиль компании: название, сфера деятельности, охват, регион, описание, логотип, стиль коммуникации |
| Активный бизнес | `BusinessModel.is_active` | Бизнес, для которого пользователь сейчас генерирует контент; у пользователя не больше одного |
| Стиль коммуникации | `communication_style` | Тон общения бренда: формальный, дружелюбный, профессиональный |
| Пост | `Post` (content_service) | Сгенерированный текст публикации с целью, тоном и платформой |
| Цель | `PostGoal` | Зачем публикуется контент: увеличить продажи, повысить вовлечённость, повысить узнаваемость, другое |
| Контент-план | `ContentPlan` | Набор идей публикаций для бизнеса на период в днях |
| Идея контент-плана | `ContentPlanItem` | Один пункт плана: дата, заголовок, описание идеи, формат, цель |
| Популярный пост | `TelegramPost` | Публикация Telegram-канала из топ-5 по просмотрам за выбранный период |
| Демо-режим | `*_MOCK`, `SMTP__MODE=console` | Работа без внешних сервисов: заглушки LLM и Telegram, код подтверждения в логе |

## 2. Требования к функционалу

### 2.1. Функциональные требования

| ID | Требование | Приоритет | Состояние | Признак выполнения |
|---|---|---|---|---|
| FR-1 | Пользователь может зарегистрироваться по email и паролю и подтвердить email кодом из письма | Обязательно в этом семестре | есть | После ввода верного кода учётная запись помечена подтверждённой, пользователь попадает на главную страницу. Пока email не подтверждён, войти нельзя: вместо входа предлагается ввести код |
| FR-2 | Пользователь может войти по email и паролю и оставаться в системе, не вводя пароль повторно, пока действует сессия | Обязательно в этом семестре | доработать | Вход по паре email + пароль открывает главную страницу. По истечении access-токена он обновляется по refresh-токену без участия пользователя. Вход по имени пользователя не принимается (сейчас принимается) |
| FR-3 | Пользователь может восстановить забытый пароль по коду из письма | Обязательно в этом семестре | есть | После ввода кода и нового пароля вход со старым паролем отклоняется, с новым — проходит |
| FR-4 | Пользователь может создать, отредактировать и удалить профиль бизнеса (название, сфера, охват, регион, описание, логотип, стиль коммуникации) — не больше двух бизнесов | Обязательно в этом семестре | доработать | Созданный бизнес появляется в списке, изменения сохраняются, удалённый исчезает. При попытке создать третий бизнес пользователь видит сообщение о лимите (сейчас — HTTP 500 «failed to create business») |
| FR-5 | Пользователь может переключаться между своими бизнесами без выхода из аккаунта | Обязательно в этом семестре | есть | После выбора бизнеса в шапке все генерации используют данные выбранного бизнеса; выбор сохраняется после перезагрузки страницы |
| FR-6 | Пользователь может получить самые просматриваемые посты Telegram-канала за выбранный период | Обязательно в этом семестре | есть | Для существующего публичного канала и периода с публикациями показывается до 5 постов с текстом, числом просмотров и датой, отсортированных по убыванию просмотров |
| FR-7 | Пользователь может сгенерировать новый пост на основе выбранных популярных постов Telegram | Обязательно в этом семестре | есть | После выбора 1–5 постов и нажатия «Сгенерировать» показывается новый текст в стиле выбранных публикаций, не копирующий их дословно |
| FR-8 | Пользователь может сгенерировать пост для бизнеса, указав описание, цель и тон, и отредактировать, скопировать и сохранить результат | Обязательно в этом семестре | доработать | По заполненной форме показывается текст поста, учитывающий профиль бизнеса; текст можно изменить и скопировать одной кнопкой. Пустое описание отклоняется с понятным сообщением (сейчас — «failed to generate business post») |
| FR-9 | Пользователь может сгенерировать контент-план на заданный срок и число идей, отредактировать его (изменить, удалить, добавить идею) и сохранить | Обязательно в этом семестре | доработать | План содержит ровно указанное число идей, у каждой есть дата в пределах срока, заголовок, описание и формат. Изменения пользователя сохраняются на сервере и видны после перезагрузки (сейчас дат нет, редактирования и сохранения нет) |
| FR-10 | Пользователь может просмотреть историю сгенерированных постов и контент-планов своего бизнеса | Желательно | доработать | На странице истории видны все посты и планы бизнеса в порядке убывания даты, в том числе с другого устройства (сейчас история постов только в localStorage браузера, история планов отсутствует) |

За пределами семестра (приоритет «потом», номера не присваиваются): генерация изображений, экспорт в PDF/ZIP/Word, фирменные цвета бренда, тарифы и оплата, переработка готового текста через ИИ, платформа VK, административная панель.

## 3. Пользовательские сценарии

Формат: «Я как ‹роль› имею ‹вход›, делаю ‹шаги›, получаю ‹результат›».

### US-1. Регистрация и подтверждение email (FR-1)

Я как **новый пользователь** имею email, к которому есть доступ, и придуманный пароль. Делаю:
1. открываю приложение и выбираю «Регистрация»;
2. ввожу имя пользователя, email и пароль дважды;
3. получаю письмо с шестизначным кодом и ввожу его на странице подтверждения.

Получаю подтверждённую учётную запись и попадаю на главную страницу.

- **Вход:** имя пользователя, email, пароль, повтор пароля, код из письма.
- **Выход:** главная страница. В системе создана запись пользователя с `confirmed = true`, браузер хранит access- и refresh-токены.

**Пример.** Имя `kofeinya_acme`, email `owner@acme-coffee.ru`, пароль `Coffee2026`. Письмо содержит код `482913`. После ввода кода открывается главная страница с предложением «Добавить бизнес». `POST /api/v1/auth/confirm` возвращает `200` и `"confirmed": true`.

**Неверные или неполные данные:**

| Ввод | Что видит пользователь | Чего система не делает |
|---|---|---|
| Email без `@` (`owner.acme-coffee.ru`) | «email must contain @», HTTP 400 | Не создаёт пользователя, не отправляет письмо |
| Пароль `coffee` (нет цифры) или `c0f` (короче 5 символов) | «password must contain at least one digit» / «password must be at least 5 characters long», HTTP 400 | Не создаёт пользователя |
| Email уже зарегистрирован | «User already exists», HTTP 409 | Не создаёт второго пользователя с тем же email |
| Неверный код `111111` | Требуется: «Неверный код подтверждения», HTTP 400. Сейчас: «internal server error», HTTP 500 (issue) | Не подтверждает email, не выдаёт токены |

### US-2. Вход в систему (FR-2)

Я как **зарегистрированный пользователь** имею подтверждённую учётную запись (email и пароль). Делаю: открываю приложение, ввожу email и пароль, нажимаю «Войти». Получаю главную страницу со своими бизнесами.

- **Вход:** email, пароль.
- **Выход:** главная страница, токены в браузере. Неподтверждённому пользователю вместо входа предлагается ввести код (переход к шагу 3 US-1).

### US-3. Продление сессии (FR-2)

Я как **вошедший пользователь** имею истёкший access-токен и действующий refresh-токен. Делаю: продолжаю работу, например открываю список бизнесов. Получаю ответ без повторного ввода пароля: клиент сам запросил новый access-токен через `POST /auth/refresh`.

- **Вход:** refresh-токен.
- **Выход:** новый access-токен, запрошенная страница.

### US-4. Восстановление пароля (FR-3)

Я как **пользователь, забывший пароль** имею доступ к почте, указанной при регистрации. Делаю:
1. на странице входа выбираю «Забыли пароль?»;
2. ввожу email;
3. ввожу код из письма;
4. ввожу новый пароль дважды.

Получаю сообщение об успешной смене пароля и вхожу с новым паролем.

- **Вход:** email, код, новый пароль.
- **Выход:** хэш пароля в базе заменён, старый пароль больше не подходит.

### US-5. Создание и редактирование бизнеса (FR-4)

Я как **вошедший пользователь** имею меньше двух бизнесов и данные о компании. Делаю:
1. нажимаю «Добавить бизнес»;
2. ввожу название, сферу, описание; при желании — охват, регион, логотип;
3. выбираю стиль коммуникации и сохраняю.

Позже меняю описание или удаляю бизнес на странице управления. Получаю актуальный список бизнесов.

- **Вход:** название и сфера (обязательно), описание, охват, регион, логотип (PNG/JPG), стиль коммуникации.
- **Выход:** бизнес в списке. Логотип хранится в MinIO, запись — в базе бизнесов.

### US-6. Переключение между бизнесами (FR-5)

Я как **пользователь с двумя бизнесами** имею бизнесы «Кофейня Acme» и «Пекарня Acme». Делаю: выбираю «Пекарня Acme» в списке в шапке и открываю «Создать пост». Получаю форму генерации, привязанную к пекарне; сгенерированный пост учитывает её профиль.

- **Вход:** выбор бизнеса.
- **Выход:** у выбранного бизнеса `is_active = true`, у остальных — `false`.

### US-7. Анализ Telegram-канала (FR-6)

Я как **пользователь** имею имя публичного Telegram-канала (своего или конкурента). Делаю: открываю «Анализ Telegram», ввожу `@channel` и период, нажимаю «Анализировать». Получаю до 5 самых просматриваемых постов за период с текстом, просмотрами и датой.

- **Вход:** имя канала, дата начала и окончания периода.
- **Выход:** список популярных постов; в системе ничего не сохраняется.

### US-8. Пост по мотивам популярных публикаций (FR-7)

Я как **пользователь** имею результаты анализа канала (US-7). Делаю: отмечаю 1–3 поста, нажимаю «Сгенерировать пост». Получаю новый текст в духе выбранных публикаций, который могу отредактировать и скопировать.

- **Вход:** выбранные посты (id, текст, просмотры), активный бизнес.
- **Выход:** текст поста. Пост сохранён с типом «из Telegram» и ссылками на исходные посты.

### US-9. Генерация поста для бизнеса (FR-8)

Я как **пользователь** имею активный бизнес с заполненным профилем. Делаю:
1. открываю «Создать пост»;
2. ввожу описание поста;
3. выбираю цель и, при желании, тон;
4. нажимаю «Сгенерировать»;
5. правлю текст в редакторе и копирую его.

Получаю готовый к публикации текст.

- **Вход:** описание (обязательно), цель, тон (необязательно), данные активного бизнеса.
- **Выход:** текст поста на экране; пост сохранён в базе контента и добавлен в историю.

**Пример.** Бизнес «Кофейня Acme» (сфера «Еда и напитки», регион «Москва», стиль «дружелюбный»). Описание «Анонс осеннего меню: тыквенный латте и пирог с яблоком», цель «Повысить вовлечённость» (`goal = 1`), тон `friendly`. `POST /api/v1/content/generate_post/<id бизнеса>` возвращает `200` и непустое поле `generated_post`: текст на русском языке до 2000 символов, в котором упомянуты тыквенный латте и пирог, есть призыв к действию и 2–5 хэштегов. В демо-режиме текст фиксированный: «Это демо-текст поста…».

**Неверные или неполные данные:**

| Ввод | Что видит пользователь | Чего система не делает |
|---|---|---|
| Пустое описание | Требуется: «Описание поста обязательно», HTTP 400. Сейчас: «failed to generate business post», HTTP 500 (FR-8 «доработать») | Не обращается к LLM, не сохраняет пост |
| Чужой или несуществующий id бизнеса | «business not found» / доступ запрещён, HTTP 404/403 | Не раскрывает данные чужого бизнеса, не генерирует пост |
| Нет токена | «missing Authorization header», HTTP 401 | Не вызывает сервисы |
| LLM недоступен или вернул не JSON | «Не удалось сгенерировать пост, попробуйте позже», HTTP 502/500 | Не сохраняет пустой или битый пост |

### US-10. Генерация и редактирование контент-плана (FR-9)

Я как **пользователь** имею активный бизнес. Делаю:
1. открываю «Контент-план»;
2. ввожу описание фокуса, цель, количество идей и срок в днях;
3. нажимаю «Сгенерировать»;
4. меняю заголовок одной идеи, удаляю другую, добавляю свою;
5. нажимаю «Сохранить».

Получаю сохранённый план с датами публикаций.

- **Вход:** описание (необязательно), цель, количество идей (> 0), срок в днях (> 0), данные бизнеса.
- **Выход:** план из идей (дата, заголовок, описание, формат, цель), сохранённый в базе контента и доступный по `plan_id`.

**Пример.** «Кофейня Acme», цель «Увеличить продажи» (`goal = 0`), 7 идей, срок 7 дней, описание «Запуск осеннего меню». `POST /api/v1/content/generate_content_plan/<id бизнеса>` возвращает `200`, `plan_id` и ровно 7 элементов `content_plan_item`. Даты идут с завтрашнего дня по седьмой день включительно, по одной идее в день, у каждой непустые `title`, `idea`, `format`, `goal = increase_sales`. После удаления одной идеи и сохранения повторный запрос плана возвращает 6 элементов.

**Неверные или неполные данные:**

| Ввод | Что видит пользователь | Чего система не делает |
|---|---|---|
| Количество идей `0` или срок `0` | Требуется: «Количество постов должно быть больше 0» / «Период в днях должен быть больше 0», HTTP 400. Сейчас сервис проверяет, но gateway отдаёт «failed to generate content plan», HTTP 500 | Не обращается к LLM, не создаёт план |
| Срок меньше числа идей (10 идей за 3 дня) | Несколько идей на один день; даты не выходят за срок | Не ставит даты за пределами срока |
| Нечисловое значение (`"семь"`) | «invalid request payload», HTTP 400 | Не создаёт план |

### US-11. История контента (FR-10)

Я как **пользователь** имею бизнес, для которого уже генерировал посты и планы. Делаю: открываю «История», выбираю бизнес. Получаю список постов и планов с датами создания, могу открыть и скопировать любой.

- **Вход:** выбранный бизнес.
- **Выход:** список, отсортированный по дате (новые сверху); данные берутся с сервера и одинаковы на любом устройстве.
